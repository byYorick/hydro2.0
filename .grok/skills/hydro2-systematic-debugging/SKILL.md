# Системная отладка Hydro 2.0

## Локализуй отказ

Зафиксируй наблюдаемый симптом, ожидаемое поведение, среду/коммит и точный способ воспроизведения. Прочитай короткий хвост ошибки и релевантный diff; не начинай со сброса БД или переписывания архитектуры.
Для command path проследи идентификаторы: Laravel intent/idempotency_key → ae_tasks → ae_commands.external_id → commands.cmd_id → MQTT command_response. Секреты и полные payload с credentials в отчёт не включай.
Для telemetry проверь topic, metric_type/value/ts, HL ingest и запись sensors/telemetry_last. Прохождение JSON Schema не доказывает прохождение всего pipeline.

## Проверь гипотезу

1. Найди последнее подтверждённое событие на каждой границе и первую отсутствующую/ошибочную запись.
2. Сравни с рабочим аналогом и текущим контрактом. Busy/lease, timestamp/HMAC, offline-нода, stale telemetry и ошибка read-model требуют разных действий.
3. Сформулируй одну проверяемую причину и сделай минимальную проверку. Если она не подтверждена, обнови гипотезу; не накапливай случайные retry/fallback.
4. Работай в пределах запроса. Не обходи fail-closed, не публикуй MQTT напрямую и не добавляй новую подсистему ради симптома.

## Исправь и проверь

Для значимого бага выбери воспроизводимый сценарий/существующий целевой тест. Новый regression test нужен, когда защищает важное поведение; опечатка не требует нового тестового набора.
Запусти проверку слоя в Docker, firmware — в ESP-IDF. Перед Playwright объясни узкий scope; realhw использует отдельный guide и MQTT 1884. Не переходи к полному suite после уже достаточной успешной проверки без причины.
Для two-tank применяй two-tank-debug и текущий RuntimePlan. Не пересылай насосную дозу для проверки доставки.

## Результат

Отдели наблюдения, подтверждённую причину и гипотезы. Укажи исправление и реально выполненную проверку; чтение теста, отсутствие ошибки в логах и успешная модельная оценка — разные виды доказательств.
